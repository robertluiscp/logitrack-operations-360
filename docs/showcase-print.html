O que é

Uma operação logística inteira, modelada no Salesforce

O projeto reproduz a rotina de uma transportadora de encomendas fictícia — LogiTrack Brasil — inspirada na operação real de um carrier de última milha, com empresa, marcas e dados anonimizados.

São cinco áreas de negócio conectadas: bases de entrega (Regional → Centro de Distribuição → Base, com 166 bases carregadas de um arquivo real de cidades do Sul do Brasil), comercial (embarcadores, contratos, faturamento), cadastro e frota (motoristas terceirizados nos modelos TAC / MEI / ETC / MR / Coleta, cada um com regras próprias), SAC (chamados, PNR — “paguei não recebi”) e prevenção de perdas (apuração de extravios e penalização de motorista), fechando no financeiro de contas a pagar.

Nenhum código Apex de produção. O objetivo é demonstrar domínio da configuração declarativa — clicks, not code — no nível de quem concluiu as trilhas Administrador Básico e Intermediário do Trailhead e sabe aplicá-las juntas, num sistema que faz sentido de ponta a ponta.

Arquitetura de dados

As cinco áreas são integradas, não cinco apps soltos

Os objetos se referenciam entre domínios: uma remessa aponta para o embarcador que a originou, para o motorista que a leva, para a ocorrência quando ela trava, para o extravio quando ela some — e para a solicitação de pagamento que ressarce o cliente.

As seis áreas

Cada app resolve uma parte da operação

Operations 360

Unidade Logística · Remessa · Evento de Rastreamento · Solicitação de Coleta · Romaneio · Rota · Tentativa de Entrega · Ocorrência Operacional

Da coleta à entrega. Flows agendados detectam remessas retidas e sem movimentação há +10 dias e abrem ocorrências sozinhos; um screen flow registra a tentativa de entrega com geolocalização e foto.

Comercial

Embarcador (Account) · Contrato Comercial · Faturamento Mensal · Oportunidade

Carteira e prospecção. Faturamento mensal como master-detail da conta, com roll-ups; processo de negócio de prospecção em 9 etapas com Path.

Cadastro & Frota

Motorista · Veículo · Documento do Motorista

Motorista com 5 Record Types (TAC / MEI / ETC / MR / Coleta), cada um com fórmulas derivadas do tipo — mínimo de pacotes, exigência de veículo, situação da CNH. Validação de placa Mercosul por REGEX.

SAC

Chamado (Case) · 5 filas

Cinco Record Types (PNR, avaria pós-entrega, postura do motorista…) e uma regra de atribuição que roteia por tipo para a fila certa. Flows de SLA e envelhecimento de PNR.

Prevenção de Perdas

Extravio · Penalização de Motorista

Extravio com chave externa que impede dois registros para a mesma remessa. Ressarcimento acima de R$ 300 sobe para aprovação; ao ser aprovado com culpa do motorista, um flow after-save cria a penalização automaticamente.

Financeiro

Solicitação de Pagamento · Pagamento · Despesa

Aprovação multinível por alçada: Coordenação sempre, Gerência acima de R$ 2.000, Diretoria acima de R$ 10.000. Quando os pagamentos confirmados cobrem o valor, a solicitação vira “Paga” sozinha.

Um processo de ponta a ponta

Uma remessa que não chega — até virar penalização

O cenário que junta quatro tipos de automação: flow agendado, regra de atribuição, processo de aprovação e flow disparado por registro. Tudo declarativo.

Competências de administração

O que cada trilha do Trailhead exercita — e onde está no projeto

Data ModelingBásico
20 objetos; lookup, master-detail e hierarquia; 56 fórmulas, 13 roll-ups, geolocalização, autonumber, external IDs.
Formulas & ValidationsIntermediário
110 regras de validação em 21 objetos — REGEX, ISCHANGED, PRIORVALUE, ISNEW — e fórmulas cross-object.
Data SecurityIntermediário
OWD Private / Public Read Only em 5 objetos; 8 sharing rules (owner e critério) + 3 grupos públicos; hierarquia de 17 papéis; 10 permission sets + 6 permission set groups (projeto permission-set-led).
Approval ProcessesIntermediário
2 processos; um multinível por alçada com critério de entrada por etapa; field updates de workflow nas fases inicial, final, de rejeição e de recall.
Picklist AdministrationIntermediário
63 picklists (51 restritas); global value set reutilizado; 2 picklists dependentes (motivo → sub-motivo).
Lightning Experience CustomizationBásico
6 apps, 6 home pages, 6 Lightning Record Pages (Dynamic Forms), 11 Paths, 19 compact layouts, utility bar, botões e ações rápidas.
Automação — FlowBásico + Intermediário
8 before-save · 5 after-save · 5 agendados · 1 screen flow; regra de atribuição de Case roteando para 5 filas.
Data ManagementBásico
Bulk API 2.0 com upsert por external ID (~2.800 registros); 3 matching rules + 4 duplicate rules (placa de veículo bloqueia, CPF/CNPJ alerta).
User EngagementBásico
4 prompts de In-App Guidance (um por app), com ação que leva à list view da área.
External ServicesIntermediário
Named Credential + External Service (ViaCEP, schema OpenAPI 3) + screen flow que invoca a ação para consultar endereço por CEP.
Reports & DashboardsBásico
18 relatórios com gráfico · 9 painéis em grid layout · 1 custom report type · métricas executivas (SLA, % de entregas, contas a pagar por centro de custo).

Como foi construído

Configuração declarativa, tratada como código

Salesforce DX, source-tracked

Todo o metadata versionado no Git em ~50 commits — um bloco por módulo de trabalho, mensagem descritiva, histórico auditável.

Geradores de metadata

O XML dos objetos, campos e regras foi gerado por scripts Python a partir de um módulo auxiliar comum — para manter 507 campos e 110 validações consistentes.

Bulk API 2.0 para os dados

~2.800 registros fictícios carregados por área, com upsert por external ID e tratamento de picklists restritas e limite de storage.

Autenticação JWT Bearer Flow

Deploy sem interface, via sf CLI e certificado — o mesmo que um pipeline de CI usaria.

O repositório traz um README completo, uma auditoria de competências Trailhead e a lista honesta do que ficou para configuração manual no Setup (algumas coisas realmente não passam pela Metadata API).

Três formas de avaliar

01

Ler o metadata no GitHub

Para quem conhece Salesforce: cada objeto, flow, processo de aprovação e permission set está em XML legível. Abrir o processo de aprovação de pagamento já mostra a alçada multinível.

02

Fazer o deploy num Developer Edition grátis

Uma conta Developer Edition é gratuita. Com o sf CLI, um deploy traz o ambiente inteiro em ~10 minutos — o README tem o passo a passo.

03

Ler a auditoria de competências

O arquivo AUDITORIA-TRAILHEAD.md mapeia cada módulo das trilhas Administrador Básico e Intermediário para onde ele aparece no projeto — sem precisar instalar nada.
